# H-031: Recovery Key Uses Raw SHA-256 Instead of Password-Hashing KDF

**Priority:** High
**Conflict Type:** bad_implementation
**Spec Reference:** Main Spec §7.8, §8; Non-Negotiable Rule Set §3 (#5 never logs secrets)

**Status:** Not Started
**Branch:** 

## Description

`KeyDerivation.HashRecoveryKeyForVerification()` in `src/Hashi.Infrastructure/Crypto/KeyDerivation.cs` hashes recovery keys using raw SHA-256:

```csharp
public static string HashRecoveryKeyForVerification(string recoveryKey)
{
    var hash = SHA256.HashData(Encoding.UTF8.GetBytes(recoveryKey));
    return Convert.ToHexString(hash).ToLowerInvariant();
}
```

Recovery keys generated by `RecoveryKeyGenerator` are human-readable strings (default: 8 groups of 4 chars, Crockford base32 alphabet). While this provides ~128 bits of entropy, a recovery key is fundamentally a **human-remembered or human-stored secret** with significantly lower practical entropy than a cryptographic random key. Such secrets should be protected with a slow, memory-hard password-hashing function (Argon2id) or at minimum PBKDF2 with a high iteration count.

SHA-256 is designed to be fast, making offline brute-force attacks against stolen `VaultWrappedKeyEntity.RecoveryKeyHash` values practical if a database dump is obtained.

## Evidence

- `KeyDerivation.cs:22-26` — Raw SHA-256 hashing
- `RecoveryKeyGenerator.cs` — 8×4 char Crockford base32 (~128 bits entropy, but Crockford reduces effective search space)
- `VaultWrappedKeyEntity.cs` — `RecoveryKeyHash` is a `string` stored in the database

The spec §8 states: "Admin vault keys are wrapped by passkey PRF output where supported and by the recovery key." and §7.8: "recovery key becomes the vault unlock mechanism." If the vault's security depends on the recovery key, the recovery key hash must be computationally expensive to crack.

## Expected Outcome

Recovery key verification should use Argon2id (preferred) or PBKDF2-HMAC-SHA256 with:
- Salt: per-deployment random salt stored alongside the hash
- Memory cost: minimum 64 MiB (Argon2id)
- Iterations/time cost: tuned for ~1 second on target hardware
- Parallelism: 1 (single-threaded verification)

## Fix Guidance

1. Add Argon2id support via `System.Security.Cryptography` (available in .NET 8+) or a well-maintained library like `Konscious.Security.Cryptography.Argon2`.
2. Store salt alongside the hash in `VaultWrappedKeyEntity` (add `RecoveryKeyHashSalt` field).
3. Fall back to PBKDF2 with minimum 600,000 iterations if Argon2id is not available.
4. Update `KeyDerivation.HashRecoveryKeyForVerification` to use the new KDF.
5. Update `VaultService` recovery key comparison to match the new hash format.

## Acceptance Criteria

- [ ] Recovery key hash is computed using Argon2id or PBKDF2 with iterations >= 600,000
- [ ] Salt is random per-deployment and stored alongside the hash
- [ ] Hash verification takes >= 500ms on target hardware
- [ ] Existing recovery keys are migrated or setup re-triggers hash recomputation
- [ ] Recovery key brute-force unit test verifies computational cost (mock time)
