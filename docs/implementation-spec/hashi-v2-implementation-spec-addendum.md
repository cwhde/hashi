# Hashi V2 Addendum: Extended IP Security, CAPTCHA Challenge Flow, Agent-Bound Connections, Internal Agent DNS, and CI/CD Optimization

## 1. Purpose

This document extends the Hashi V2 implementation specification with five related feature areas:

1. Extended IP and security subject management.
2. External IP blocklist management.
3. Self-hosted CAPTCHA challenge integration using an existing Cap instance.
4. Agent-bound connection targets and internal agent DNS.
5. CI/CD performance optimization for Hashi, Hashi Pulse, and Hashi legacy images.

The goal is to make Hashi’s abuse/security layer operationally useful, configurable, auditable, and consistent with the existing Hashi principles: secure by default, idempotent, previewable, recoverable, and conservative about destructive or traffic-blocking changes.

This addendum does not replace the existing Hashi V2 specification. It refines and extends the existing security, resource, AdGuard, Pulse, setup, and CI/CD sections.

## 2. Non-Goals

The following are explicitly out of scope:

1. Rewriting the Pulse agent from Go.
2. Deploying or managing the lifecycle of the Cap server container.
3. Using `hashi.home.arpa` as a reverse-proxy domain.
4. Making manual allowlist entries bypass SSO or CAPTCHA by default.
5. Enabling third-party blocklists automatically without explicit user selection.
6. Removing linux/arm64 support from Hashi, Hashi Pulse, or Hashi legacy images.
7. Encoding runner host/docker-compose configuration into the Hashi product specification.

## 3. Terminology

### Security Subject

A security subject is an entity Hashi can observe, challenge, allow, block, or escalate. Supported subject types:

* IP address.
* CIDR range.
* Country.
* Region.
* ASN.
* User/session identity, where available.
* Composite subject, such as IP + resource or IP + root domain, for rate buckets.

### Manual Allow

A manually configured security exception that prevents Hashi-controlled blocking and escalation for a subject.

Manual allow does not bypass SSO or CAPTCHA in this version.

### Manual Block

A manually configured block entry that denies access for a subject.

Manual block is stronger than adaptive challenge/soft-block state and should be visible in all effective-decision views.

### Challenge

A CAPTCHA requirement triggered by rate limits, suspicious behavior, resource rules, or manual security action.

A challenge is not a long-term whitelist and does not grant a free browsing window. It only clears the active challenge state and resets or decays the triggering buckets after successful solve.

### Soft Block

A middleware-level block enforced by Hashi forward-auth and related Hashi-controlled middleware. It does not necessarily install firewall rules.

### Firewall Block

A host-level block installed through Hashi-managed firewall chains/sets. Only IP and CIDR subjects are eligible for firewall enforcement by default.

### Agent Binding

A connection target mode where a Hashi connection uses the currently selected IP of a Pulse agent instead of a static host/IP.

Example: an AdGuard Home connection may target agent `kanae`, selected private IP, port `3000`.

### Internal Agent DNS

AdGuard Home rewrites generated by Hashi for Pulse agents under an internal domain such as `hashi.home.arpa`.

Example: `kanae.hashi.home.arpa -> 10.0.0.42`.

Internal agent DNS is only for agent names and selected agent IPs. It is not a reverse-proxy routing layer.

## 4. Compatibility With Existing Spec

The implementation must preserve these existing Hashi rules:

1. Hashi only modifies objects it created, imported, or the user explicitly assigned to Hashi.
2. Hashi never touches unrelated firewall state.
3. Firewall changes must use Hashi-owned chains and sets.
4. Traefik, firewall, DNS, and AdGuard changes must be generated through sync plans with preview, apply, result, and audit logs.
5. Required system resources cannot be deleted while required for app access.
6. Optional generated resources may be user-deletable unless required by an active feature.
7. AdGuard Home remains optional.
8. Pulse agents remain optional.
9. The Pulse agent remains implemented in Go.
10. All timestamps are UTC in storage and rendered in browser locale.
11. Unsafe admin endpoints require CSRF protection.
12. High-risk security operations require recent reauthentication.

## 5. Extended Security Subject Management

### 5.1 Product Behavior

Hashi must provide a security view where the user can search for:

* A single IP address.
* A CIDR range.
* An ASN.
* A country or region.
* A known subject from recent events.

For each subject, Hashi must show:

1. Current effective decision.
2. Matching manual allow/block entries.
3. Matching blocklist entries.
4. Matching resource rules.
5. Active adaptive state.
6. Active challenge state.
7. Active soft block state.
8. Active firewall block state.
9. Ban/challenge history.
10. Recent security events.
11. Recent request bucket summary.
12. Firewall application state, where applicable.
13. Available actions.

The page must be fast enough to use as an incident response tool. It must not require manually searching logs in different UI areas.

### 5.2 Effective Decision Order

The effective decision must be derived in a deterministic order.

Recommended priority:

1. Invalid/untrusted request metadata.
2. Manual block.
3. Firewall block.
4. High-confidence blocklist with firewall enforcement.
5. Soft block.
6. Active challenge required.
7. Resource-specific rule.
8. Manual allow.
9. Default resource behavior.

Important: manual allow prevents Hashi-controlled blocking and escalation, but it does not bypass SSO or CAPTCHA in this version.

To support future behavior, manual allow entries must contain explicit bypass flags:

* `bypassBlocking`.
* `bypassAdaptiveEscalation`.
* `bypassRateLimit`.
* `bypassChallenge`.
* `bypassSso`.

Initial default:

* `bypassBlocking = true`.
* `bypassAdaptiveEscalation = true`.
* `bypassRateLimit = false`.
* `bypassChallenge = false`.
* `bypassSso = false`.

The UI must show these future-capable semantics clearly, even if only the first two flags are editable initially.

### 5.3 Subject Detail Actions

From a subject detail page, the user must be able to:

* Add manual allow.
* Add manual block.
* Remove manual allow.
* Remove manual block.
* Convert temporary block to permanent block.
* Shorten block duration.
* Extend block duration.
* Expire block immediately.
* Escalate soft block to firewall block, if subject type supports it.
* De-escalate firewall block to soft block.
* Trigger sync preview for firewall-affecting changes.
* View which resources would be affected by an action.
* View the audit trail for all manual actions.

All actions that can affect live traffic must create an audit event.

Firewall-affecting changes must not apply directly from a random button. They must produce or attach to a firewall sync plan.

### 5.4 Security Timeline

Each subject detail page must include a chronological timeline containing:

* Forward-auth decisions.
* Access-log-derived request summaries.
* WAF events.
* Rate-limit triggers.
* Challenge required events.
* Challenge solved events.
* Challenge failed events.
* Challenge ignored/escalation events.
* Soft block created/expired events.
* Firewall block created/applied/expired events.
* Manual allow/block changes.
* Blocklist hits.
* GeoIP/ASN resolution changes, if relevant.

The timeline should support filtering by event type and resource.

## 6. Ban Duration and Escalation Policy

### 6.1 Policy Model

Hashi must support configurable ban duration policies.

Do not allow arbitrary executable expressions.

Supported policy types:

1. Constant.
2. Linear.
3. Exponential.
4. Capped exponential.
5. Permanent after N offenses.

Fields:

* `base_duration_seconds`.
* `linear_multiplier`.
* `exponential_multiplier`.
* `max_duration_seconds`.
* `permanent_after_count`.
* `count_window_seconds`.
* `reset_count_after_seconds`.

Examples:

* Constant: always 3000 seconds.
* Linear: `base * offense_count`.
* Exponential: `base * multiplier^(offense_count - 1)`.
* Capped exponential: exponential, but never above max duration.
* Permanent after N: temporary until threshold, then permanent.

### 6.2 Offense Counting

Offense count must be tracked separately from active block state.

Do not reset offense history after a successful CAPTCHA solve.

Successful CAPTCHA solve may reset or decay request buckets, but it must not erase:

* Soft block count.
* Firewall block count.
* Manual block history.
* Security event history.
* Repeat-offender counters.

### 6.3 User Configuration

Settings UI must expose:

* Default challenge trigger thresholds.
* Default challenge ignored thresholds.
* Default soft block policy.
* Default firewall block policy.
* Repeat-offender escalation policy.
* Whether CAPTCHA success resets or decays the triggering rate bucket.
* Decay percentage if decay mode is selected.
* Minimum time between repeated challenges.
* Maximum challenge failures before escalation.
* Maximum requests while challenged before escalation.

Resource security profiles may override global defaults.

## 7. CAPTCHA Challenge Flow

### 7.1 Provider Choice

Hashi must initially support Cap as the CAPTCHA provider.

Hashi must not deploy Cap. It integrates with an existing Cap Standalone instance.

Setup must collect:

* Cap public challenge base URL.
* Cap site key.
* Cap secret key.
* Optional Cap admin resource details.
* Verification timeout.
* Whether instrumentation/headless detection is expected.
* Whether to create a normal Hashi resource for the Cap admin dashboard.

The Cap secret key must be stored as a service-sync secret.

The Cap site key may be visible in configuration.

### 7.2 Cap Public Challenge Resource

Hashi must create and maintain a required system resource for the public CAPTCHA challenge flow when CAPTCHA integration is enabled.

This resource:

* Is required while CAPTCHA is enabled.
* Cannot be deleted while CAPTCHA is enabled.
* Is editable only through the CAPTCHA setup/settings workflow.
* Must not require SSO.
* Must not itself require CAPTCHA.
* Must not be subject to adaptive challenge rules.
* Must still be subject to hard firewall blocks.
* Must expose only the paths required for the public challenge flow.
* Must not expose the Cap admin dashboard or management API.

The public challenge resource must use a real reverse-proxy domain, not `hashi.home.arpa`.

### 7.3 Cap Admin Dashboard Resource

Hashi may optionally create a normal reverse-proxy resource for the Cap admin dashboard.

This resource:

* Is not a required protected system resource.
* Is user-configurable.
* Is user-deletable.
* Uses a normal real-domain reverse-proxy hostname.
* Should strongly recommend SSO.
* Should strongly recommend admin-only access.
* Should not require CAPTCHA by default to avoid dependency loops.
* May still use normal rate-limit and abuse protection as long as it cannot cause a CAPTCHA dependency loop.

The UI must clearly distinguish:

* CAPTCHA public challenge resource: required system resource.
* Cap admin resource: optional normal resource.

### 7.4 Challenge State Semantics

CAPTCHA is a middle state, not a long-term allowlist.

When a subject triggers a challenge:

1. Hashi sets `challenge_required = true`.
2. Hashi records the challenge reason and triggering buckets.
3. Normal protected resources deny or redirect to the challenge flow.
4. Upstream services are not contacted while the challenge is active.
5. Requests while challenged are counted separately.
6. CAPTCHA public resource remains accessible.
7. Firewall hard blocks still take precedence.

When the subject solves CAPTCHA:

1. Hashi verifies the token with Cap.
2. Hashi records a successful challenge event.
3. Hashi clears `challenge_required`.
4. Hashi resets or decays only the triggering rate buckets.
5. Hashi clears `requests_while_challenged`.
6. Hashi clears `failed_challenge_count`.
7. Hashi does not clear offense history.
8. Hashi does not bypass SSO.
9. Hashi does not grant a long global clearance window.

There must be no default 60-minute “free pass” after solving CAPTCHA.

### 7.5 Requests While Challenged

If a subject keeps requesting protected resources after `challenge_required = true`, Hashi must treat that as a separate abuse signal.

Track:

* `requests_while_challenged`.
* `resources_hit_while_challenged`.
* `captcha_page_requests`.
* `captcha_verify_attempts`.
* `failed_challenge_count`.
* `challenge_ignored_count`.

Default behavior:

* Initial threshold breach: require CAPTCHA.
* Continued protected-resource hits while challenged: keep denying cheaply.
* Excessive hits while challenged: soft block.
* Severe repeated hits while challenged: firewall block if subject type supports it.
* Repeated challenge/solve/abuse loops: escalate according to repeat-offender policy.

Suggested initial defaults:

* Challenge ignored threshold: 30 protected-resource hits while challenged within 5 minutes.
* Soft block after ignored threshold: 10 minutes.
* Firewall block threshold: 100 protected-resource hits while challenged within 5 minutes, or repeated ignored-threshold violations.
* Failed challenge threshold: 5 failed verifies within 10 minutes causes soft block.
* Repeated challenge/solve/abuse cycles: use ban duration multiplier.

These defaults must be configurable.

### 7.6 API and Browser Behavior

For browser-like requests:

* Redirect to the Hashi challenge page.
* Preserve the originally requested URL.
* After successful challenge, redirect back to original URL.
* If the original URL is unsafe or cross-origin, redirect to resource root.

For API-like requests:

* Return `403` or `429`.
* Include a machine-readable `challenge_required` response.
* Do not redirect blindly if `Accept` or request type suggests API/client traffic.

### 7.7 Challenge Page

The challenge page must:

* Be minimal.
* Load only required assets.
* Not require SSO.
* Not call protected APIs.
* Show the resource/domain the user attempted to access.
* Submit Cap token to Hashi, not directly to arbitrary upstreams.
* Handle verification failure without leaking secret details.
* Avoid exposing Cap secret key or admin API key to the client.

### 7.8 Rule Engine Integration

CAPTCHA must be a rule action, not hardcoded one-off middleware.

Rule actions:

* Allow.
* Deny.
* Require SSO.
* Require challenge.
* Soft block.
* Firewall block.
* Bypass blocking, where manual allow applies.

Rule inputs:

* Subject state.
* Resource security profile.
* Request bucket state.
* Manual allow/block entries.
* Blocklist matches.
* GeoIP/ASN data.
* Challenge state.
* Requests while challenged.
* Failed challenges.
* Previous escalations.

Rules must be explainable. The subject detail page must show why a challenge/block decision happened.

## 8. IP Blocklist Management

### 8.1 Setup Flow

Blocklists must be offered during setup as individual options.

Setup must not include a single vague “enable blocklists” toggle.

Each list must show:

* Name.
* Source URL.
* Description.
* Expected false-positive risk.
* Update frequency.
* Format.
* Enforcement mode.
* Whether it can be firewall-enforced.
* Whether it requires license/user responsibility note.

All recommended lists are disabled unless the user explicitly selects them.

The same configuration must be available later under Security Settings.

### 8.2 Default Suggested Feeds

Initial suggested feeds:

1. Feodo Tracker Botnet C2 IP blocklist.
2. Spamhaus DROP.
3. Spamhaus DROPv6.
4. DShield recommended block list.
5. FireHOL Level 1.
6. Custom URL.

Hashi must not silently enable any feed.

Hashi must include a warning that third-party blocklists can create false positives and may block legitimate traffic.

### 8.3 Custom URL Blocklists

The user can add a custom blocklist by pasting a URL.

No file upload is required for v1.

Allowed URL requirements:

* HTTPS only by default.
* Optional HTTP only if explicitly allowed with warning.
* No local/private/link-local/multicast target after DNS resolution.
* No redirect to private/internal addresses.
* Max redirect count.
* Max response size.
* Request timeout.
* User-agent identifying Hashi.
* ETag and Last-Modified support where available.
* TLS certificate validation required.

Hashi must prevent SSRF.

Blocked target ranges for fetcher:

* Loopback.
* RFC1918 private IPv4.
* Link-local.
* Multicast.
* Unique-local IPv6.
* Link-local IPv6.
* Metadata service IP ranges.
* Docker bridge ranges, unless explicitly allowed for local testing in dev mode.

### 8.4 Supported Formats

v1 must support:

1. Plain line-based IP/CIDR lists.
2. Plain line-based lists with comments.
3. FireHOL-style `.ipset` / `.netset`.
4. CSV/TSV with configurable column.
5. JSON array of strings.
6. JSON object containing an array field selected by config.

Out of scope for v1:

* Full Suricata rule parsing.
* Full Snort rule parsing.
* Domain blocklists.
* URL blocklists.
* Threat-intel formats requiring complex nested schemas.

### 8.5 Parsing Rules

Parser must:

* Normalize IPv4/IPv6.
* Normalize CIDR ranges.
* Reject invalid entries.
* Deduplicate entries.
* Preserve source attribution.
* Preserve line number where possible.
* Record parse errors.
* Record ignored entries.
* Support preview before enabling.
* Never partially apply a failed update without recording status.

### 8.7 Enforcement

IP/CIDR blocklists may be enforced in:

* Forward-auth middleware.
* Hashi-generated Traefik config where practical.
* Firewall sets/chains.

Country/ASN blocklist-like rules are forward-auth only by default and must not be expanded into firewall IP ranges unless explicitly implemented later.

Blocklist firewall changes must use sync preview/apply/result.

### 8.8 Expiry and Staleness

If a blocklist fails to update:

* Keep the last known good entries.
* Mark the source degraded.
* Show last success time.
* Show last error.
* Do not delete all entries because one fetch failed.

If a source is disabled:

* Remove its entries from effective decisions.
* Queue firewall sync if firewall-applied entries existed.
* Keep historical fetch runs and events.

## 9. Agent-Bound Connections

### 9.1 Purpose

Hashi connections that currently require a fixed host/IP must also support a Pulse agent target.

The agent’s selected IP becomes the host/IP Hashi uses to contact that external service.

This applies to connection targets such as:

* AdGuard Home instance.
* Traefik host.
* Linux firewall host, where meaningful.
* Future service connections.

Example:

Instead of configuring AdGuard as `10.0.0.50:3000`, the user configures:

* Target mode: Pulse agent.
* Agent: `kanae`.
* Agent IP selection: selected private IP.
* Port: `3000`.
* Scheme: `http` or `https`.

Hashi resolves the current selected IP from Pulse state and uses that IP when calling AdGuard.

### 9.2 Target Model

Add reusable connection target model.

Fields:

* `target_mode`: `static_host`, `static_ip`, `pulse_agent`.
* `static_host`.
* `static_ip`.
* `pulse_agent_id`.
* `pulse_ip_mode`: `selected`, `public`, `private_selected`, `private_candidate`.
* `private_candidate_selector`.
* `port`.
* `scheme`.
* `path_prefix`.
* `tls_validation_mode`.
* `expected_hostname`.
* `resolved_ip_snapshot`.
* `last_resolved_at_utc`.
* `resolution_status`.
* `resolution_error`.

### 9.3 Pulse IP Modes

Supported modes:

* `selected`: use the agent’s selected IP.
* `public`: use the remote source IP from heartbeat.
* `private_selected`: use selected private IP.
* `private_candidate`: choose from candidates by interface name, CIDR match, or explicit address.

The UI should default to `selected`.

The UI must show:

* Last seen.
* Current public IP.
* Private IP candidates.
* Selected IP.
* Stale status.
* Whether the selected IP is reachable from Hashi.

### 9.4 Behavior on Agent IP Change

When an agent-bound connection changes resolved IP:

1. Hashi records the new resolved target.
2. Hashi marks dependent connection health as pending.
3. Hashi queues relevant sync/reconcile jobs.
4. Hashi does not rewrite unrelated resources.
5. Hashi shows dependency impact in activity logs.

### 9.5 Validation

Before saving an agent-bound connection:

* Agent must exist.
* Agent must have heartbeat unless user allows saving inactive target.
* Selected IP mode must be valid.
* Port must be valid.
* Hashi should perform optional connectivity test.
* Connectivity test failure must not reveal secrets.
* Saving inactive/unreachable targets requires explicit confirmation.

## 10. Internal Agent DNS

### 10.1 Purpose

Hashi must generate internal DNS names for Pulse agents through AdGuard Home rewrites.

Default domain:

* `hashi.home.arpa`.

Example:

* `kanae.hashi.home.arpa -> 10.0.0.42`.

This is for internal service configuration, humans, scripts, Docker containers, and tools that need stable names instead of hardcoded IPs.

It is not used as a reverse-proxy routing domain.

### 10.2 Rules

Internal agent DNS:

1. Applies only to Pulse agents.
2. Uses the agent’s normalized name.
3. Resolves to the agent’s selected IP.
4. Is generated through AdGuard Home rewrites.
5. Coexists with existing real-domain internal rewrites.
6. Must not replace existing real-domain rewrites.
7. Must not create Traefik routers for `hashi.home.arpa`.
8. Must not imply that HTTP/HTTPS resources are available on `hashi.home.arpa`.
9. Must never touch manual AdGuard rewrites not owned by Hashi.

### 10.3 Name Normalization

Agent DNS names must be normalized:

* Lowercase.
* ASCII slug.
* Replace spaces/invalid chars with hyphens.
* Collapse repeated hyphens.
* Trim leading/trailing hyphens.
* Reject empty result.
* Prevent collisions.

If two agents normalize to the same name, the UI must require manual override.

### 10.4 Settings

Add settings:

* Enable internal agent DNS.
* Internal agent DNS domain, default `hashi.home.arpa`.
* Per-agent DNS enabled.
* Per-agent DNS name override.
* IP mode for DNS: selected/private/public, default selected.
* Whether stale agents keep last DNS record or mark degraded.

### 10.5 AdGuard Sync

AdGuard internal agent DNS sync must:

* Use existing AdGuard ownership handling.
* Never delete manual rewrites.
* Create/update/delete only Hashi-owned internal agent DNS entries.
* Produce preview/apply/result.
* Record audit events.
* Show last applied hash.

### 10.6 Stale Agent Behavior

If an agent becomes stale:

Default behavior:

* Keep last known DNS rewrite.
* Mark record stale in UI.
* Do not delete automatically.

Optional future setting:

* Remove rewrite after configured stale duration.

This must not be default because deleting DNS entries during temporary agent outages can break dependent services.

## 14. Forward-Auth Decision Flow

The forward-auth endpoint must evaluate in this order:

1. Parse request metadata.
2. Resolve resource.
3. Resolve subject.
4. Load effective manual entries.
5. Load active block/challenge state.
6. Evaluate blocklist matches.
7. Evaluate resource security rules.
8. Evaluate rate buckets.
9. Decide action.
10. Record event.
11. Return response.

Decision actions:

* Allow upstream.
* Require SSO.
* Require challenge.
* Deny soft block.
* Deny firewall-blocked.
* Deny manual block.
* Redirect browser to challenge.
* Return API challenge response.

Upstream services must not receive requests while the subject is actively challenged or blocked.

## 15. Firewall Integration

Only IP and CIDR subjects may be firewall-enforced by default.

Firewall sync must:

* Use Hashi-owned chains/sets only.
* Never flush unrelated firewall state.
* Preview changes.
* Apply atomically where possible.
* Roll back or report partial failure.
* Track applied hosts.
* Track last applied hash.

Firewall block entries must record:

* Target host.
* Applied state.
* Last apply result.
* Last apply error.
* Last hit time, where counters are available.

ASN/country/region blocks remain forward-auth only by default.

## 17. CI/CD Performance Optimization

### 17.1 Purpose

Hashi workflows must remain strict but avoid wasting time on repeated restores, repeated image builds, and emulated ARM64 build stages.

The CI/CD changes are part of Hashi’s implementation quality requirements, not user-facing product features.

### 17.2 Non-Negotiable CI Requirements

1. Hashi main image remains linux/amd64 and linux/arm64.
2. Hashi legacy image remains linux/amd64 and linux/arm64.
3. Hashi Pulse image remains linux/amd64 and linux/arm64.
4. ARM64 builds must use cross-compilation where possible instead of QEMU emulation.
5. Dependency caches must be used for NuGet, pnpm, Go module/build caches, and Playwright where practical.
6. Docker BuildKit registry cache must remain enabled.
7. Workflows must avoid rebuilding the same Docker image for separate scan/publish jobs where practical.
8. Security scans must still run.
9. The codebase must still pass formatting, tests, audits, secret scanning, SAST, filesystem scan, and container scan.
10. Workflow changes must preserve Gitea compatibility.

### 17.3 Main Hashi Dockerfile

The main Dockerfile must be changed to be cross-build aware.

Requirements:

* Use BuildKit syntax supporting cache mounts.
* Pin build stages to `$BUILDPLATFORM`.
* Use `TARGETARCH` for .NET publish target architecture.
* Avoid running Node and .NET SDK build stages under ARM64 emulation on AMD64 runners.
* Cache pnpm store.
* Cache NuGet packages.
* Keep final runtime image target-platform correct.
* Preserve healthcheck and exposed ports.

Required pattern:

* `FROM --platform=$BUILDPLATFORM node:... AS web-build`.
* `FROM --platform=$BUILDPLATFORM mcr.microsoft.com/dotnet/sdk:... AS dotnet-build`.
* Use `ARG TARGETARCH`.
* Map Docker arch values to .NET runtime architecture where needed.
* Run `dotnet restore` with cache mount.
* Run `dotnet publish` with target architecture.
* Keep final `aspnet` image platform implicit so Buildx selects target platform.

### 17.4 Pulse Dockerfile

The Pulse Dockerfile must be changed to be cross-build aware.

Requirements:

* Use `FROM --platform=$BUILDPLATFORM golang:... AS build`.
* Use `ARG TARGETOS`.
* Use `ARG TARGETARCH`.
* Build with `GOOS=$TARGETOS`.
* Build with `GOARCH=$TARGETARCH`.
* Keep `CGO_ENABLED=0`.
* Use Go build cache mount.
* Use Go module cache mount where useful.
* Keep distroless final image.

This prevents the ARM64 Docker image build from compiling Go under emulation.

### 17.5 Hashi Legacy Dockerfile

Hashi legacy must remain multi-arch.

Requirements:

* Keep `linux/amd64,linux/arm64`.
* Optimize Dockerfile caching.
* Split dependency install from source copy where possible.
* Use BuildKit cache mounts for package manager caches.
* Avoid unnecessary native rebuilds.
* Avoid repeated install steps.
* Preserve legacy behavior and image tag.
* Do not make legacy AMD64-only.

### 17.6 CI Workflow

The CI workflow must:

* Keep path filtering.
* Use hosted tool cache where available.
* Use dependency caches.
* Cache NuGet packages.
* Cache pnpm store.
* Cache Go module/build data.
* Avoid installing ShellCheck via apt on every run if a cached/action-provided path is available.
* Avoid Playwright browser install on jobs where frontend/E2E did not change.
* Keep OpenAPI contract verification.
* Keep backend tests.
* Keep frontend check/lint/test/build.
* Keep Pulse vet/test/build.

Recommended cache areas:

* `~/.nuget/packages`.
* pnpm store path.
* `~/.cache/go-build`.
* Go module cache.
* Playwright browser cache, if stable in Gitea.

### 17.7 Security Workflow

The security workflow must:

* Keep Gitleaks.
* Keep .NET vulnerable package check.
* Keep frontend audit.
* Keep Semgrep.
* Keep Trivy filesystem scan.
* Keep Trivy container image scan.

Optimization requirements:

* Cache downloaded/scanner tools where possible.
* Cache Semgrep environment or use a container/action that avoids reinstalling on every run.
* Cache NuGet/pnpm before audits.
* Avoid rebuilding the release image separately if the publish workflow already built it.
* Prefer scanning the exact pushed image digest for main/tag release builds.
* For PRs/branches, allow a local image build for scan if no published digest exists.
* Use path filters so unrelated docs-only changes do not run heavy scans unless manually dispatched or scheduled.

### 17.8 Docker Build Workflows

Main build workflow must:

* Build linux/amd64 and linux/arm64.
* Push to configured registry.
* Keep tags: latest for default branch, SHA, semver.
* Keep registry build cache.
* Use cross-build-aware Dockerfile.

Pulse build workflow must:

* Keep native binary artifact build for amd64 and arm64.
* Keep checksums.
* Keep release attachment on tags.
* Keep Docker multi-arch image.
* Use cross-build-aware Dockerfile.

Legacy build workflow must:

* Keep linux/amd64 and linux/arm64.
* Keep old tag.
* Keep registry build cache.
* Use optimized legacy Dockerfile.

### 17.9 Avoid Duplicate Builds

The workflow design must reduce duplicate expensive work.

Target behavior:

* CI validates source.
* Security validates source and scans images.
* Publish builds release images.
* Security should scan release image digest when available instead of building the same image again.
* PR/local security may still build a local single-platform image if needed.

Do not remove required security coverage to make builds faster.

### 17.10 Cache Failure Behavior

Cache misses must not fail builds.

Cache restore/save failures should warn but not fail, unless the build specifically depends on a generated artifact.

The workflow logs should make it clear whether caches were hit or missed.

## 20. Acceptance Criteria

The feature is complete when:

1. A user can search an IP and see effective decision, history, events, rules, blocks, challenges, and blocklist hits.
2. A user can manually allow/block IPs and ranges.
3. Manual allow prevents Hashi-controlled blocking/escalation but does not bypass SSO or CAPTCHA.
4. Ban duration policy is configurable without unsafe eval.
5. Blocklists are individually selectable in setup and settings.
6. Custom blocklist URL fetch is SSRF-protected.
7. Blocklist entries can be enforced at middleware and firewall level where supported.
8. Cap integration works with an existing Cap instance.
9. CAPTCHA challenge endpoint cannot be deleted while CAPTCHA is enabled.
10. Cap admin dashboard is an optional normal resource, not a required protected system resource.
11. CAPTCHA solve clears current challenge and resets/decays triggering buckets only.
12. Continued spam while challenged escalates to soft/firewall block.
13. AdGuard and other supported connections can target Pulse agents instead of static IPs.
14. Internal agent DNS creates `agent.hashi.home.arpa` rewrites without replacing real-domain rewrites.
15. No reverse-proxy routing is generated for `hashi.home.arpa`.
16. Pulse remains Go.
17. Hashi main, pulse, and legacy images remain multi-arch.
18. Docker builds use cross-compilation where practical instead of ARM64 emulation.
19. CI uses dependency/tool caches where available.
20. Security checks remain strict and are not removed for speed.
